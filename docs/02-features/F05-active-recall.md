# F05 · 白纸召回

> 给一个概念名（如"肝"），用户在空白文本框写出所有能想起来的属性。系统对比模板给反馈。是检索练习的最强形式，也是本产品与多邻国类工具的**核心差异化**之一。

## Why

题目类型 1-7（F03）都有一个共同弱点：**线索量大**。
- 单选题：题干 + 5 选项 = 大量线索
- 填空题：题干 + 上下文 = 部分线索
- 推导题：明确的推导对象

但真实考场和临床场景中，**线索经常是最少的**——你只看到一个"肝"字，需要在大脑里把所有相关知识网络瞬间激活。这种「最小线索 → 最大召回」的能力，只有白纸召回能训练。

认知科学依据：**生成效应（Generation Effect）** + **自由召回（Free Recall）** 是所有检索形式中记忆固化效果最强的（Roediger 2006、Karpicke 2012）。

---

## 用户行为

进入白纸召回的入口：
1. 节点页底部的「白纸召回」按钮
2. 主页「想做点什么？」可加一个选项「挑战白纸召回」

用户能做的：
1. 看到一个概念名 + 空白文本框
2. 自由输入所有能想起的知识点
3. 提交后看到对比反馈（命中 / 遗漏 / 额外）

## 关键技术挑战：用户输入 → 评分

这是 F05 最难的部分。

### 方法 1：关键词匹配（MVP 默认）

节点的模板属性 + body 中的关键短语预先抽取为 `recall_keypoints`：

```yaml
# liver.md frontmatter
recall_keypoints:
  required:
    - { id: 1, text: "主疏泄", aliases: ["疏泄", "肝主疏泄"] }
    - { id: 2, text: "主藏血", aliases: ["藏血"] }
    - { id: 3, text: "五行属木", aliases: ["木", "属木"] }
    - { id: 4, text: "在志为怒", aliases: ["怒"] }
    - { id: 5, text: "在液为泪", aliases: ["泪"] }
    # ... ~15-20 个
  optional:
    - { id: 16, text: "将军之官", aliases: [] }
    - { id: 17, text: "罢极之本", aliases: [] }
```

匹配逻辑：
- 用户输入按行 / 标点切片
- 每条切片对每个 keypoint 做包含匹配（含 aliases）
- 命中：用户切片包含 keypoint 文本
- 遗漏：keypoint 未被任何切片命中
- 额外：用户切片未匹配任何 keypoint

### 方法 2：Embedding 语义匹配（V2）

用 embedding 模型（如 `text-embedding-3-small`）：
- 离线把每个 keypoint 算 embedding
- 用户提交时，对每条切片算 embedding，与 keypoints 比对
- 余弦相似度 > 0.85 算命中

优点：能处理同义表达（"肝主疏泄气机" ≈ "主疏泄"）。
缺点：需要 API 调用 / 本地模型，增加复杂度。

**MVP 决策**：方法 1 + 简单的 aliases 列表。覆盖率不够时再升级方法 2。

## 自评机制

系统判分总有不准的情况（"肝主筋脉"算不算"在体合筋"？）。让用户自评：

```
自评这次召回质量：
[ 不太行 ]    [ 还可以 ]    [ 不错 ]
   Hard         Good          Easy
```

- 三档对应 FSRS 的 Hard/Good/Easy（Again 由系统覆盖率 < 30% 自动判定）
- 用户自评比系统判分更接近真实——尤其当系统判分边界不清时
- 这也尊重用户对自己学习的元认知

## 验收标准

MVP：

- [ ] 用户能从节点页进入白纸召回
- [ ] 文本框无线索（不显示任何字段提示）
- [ ] 计时显示（向上计时）
- [ ] 字数/行数实时显示
- [ ] 自动保存（5 秒一次）
- [ ] 提交后显示命中/遗漏/额外三组
- [ ] 用户自评 → FSRS Rating
- [ ] 强度变化展示
- [ ] 节点的 `recall_keypoints` 字段被解析

MVP 内容工程：

- [ ] L2 实体节点（~30 个）全部填写 recall_keypoints

非 MVP：

- [ ] 语义匹配（embedding）
- [ ] 「额外」条目可让用户标记"是有效知识，请加入 keypoints"（贡献机制）
- [ ] 召回历史时间线（看自己进步）

---

## 反模式

- ❌ 不显示倒计时（向上计时 OK，向下倒计时是压力）
- ❌ 不在输入过程中给提示（白纸 = 真的白纸）
- ❌ 不显示得分百分比作为主要指标——用「12/18 已命中」更具体
- ❌ 不要"超过 X% 用户"对比
- ❌ 不强制做完——用户可以随时放弃

---

## 设计依据

- **原则 4（主动检索 > 被动阅读）**：白纸召回是检索的极致形式
- **原则 5（工具 > 游戏）**：温和计时、覆盖率描述，无评分游戏化

## Open Questions

- [ ] recall_keypoints 由谁写？LLM 生成 + 人审。但 keypoint 的粒度（粗 vs 细）需要约定。
- [ ] 用户输入"主疏泄、主藏血"（两点一行用顿号分隔）vs "- 主疏泄\n- 主藏血"，匹配逻辑要不要处理？倾向于要——按所有标点切片。
- [ ] 是否要让用户在召回前选择"我要召回哪些方面"（如：只召回功能 / 只召回证型）？这会引入线索，违反白纸原则。倾向于不做。
